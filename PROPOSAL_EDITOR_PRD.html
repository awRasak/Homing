Product Requirements — as-built

The Proposal Editor

Scope · Design setup, live editing, AI generation, recipients, campaigns, dashboard, export Excludes · Homin/Becca (chat, watchlist, briefings, content pipeline) Status · Draft, reverse-documented from current implementation

Go from an existing proposal design to a personalized, on-brand document per company — without hiring a designer, and without losing the original document's exact layout. This PRD documents what the Proposal Editor does today, treats the working parts as the accepted spec, and separates that clearly from what's stubbed, duplicated, or dead.

01Problem & goals

Sending a personalized proposal to many companies today means duplicating a designed document and hand-editing it per recipient — slow, error-prone, and impossible to keep visually consistent once more than one deal type or region is involved. The Proposal Editor's job is to take a real, already-designed proposal (a PDF someone actually uses) and let its owner regenerate the parts that should change per recipient — headline, opening, sourcing — while everything else on the page stays pixel-identical to the original.

Three ideas run through the whole feature set:

  • The uploaded document is the source of truth. Branding, layout, and copy are extracted from it, not rebuilt from a generic template.
  • Editing happens in place. Text blocks are edited directly on the rendered page, not in a disconnected form that redraws a mockup.
  • One design, many companies, many channels. A design is reused across a recipient list, a bulk email campaign, and a personal dashboard of past sends.

02Target user

Someone doing outreach at volume — a founder, an agency, a small BD team — who already has one or more designed proposals and needs tailored versions sent to many prospects without a designer or developer in the loop. They think in terms of designs (a proposal template with its own branding) and companies (one generated, personalized proposal per recipient).

03Design setup & import

A design captures everything reusable across every proposal generated from it: sender identity, brand color, fonts, a writing-style sample, and the static sections that don't change per recipient (pricing, process, "why us"). It can be built from scratch, or — the common path — extracted from an uploaded PDF.

Import pipeline

Every page of the uploaded file is rasterized client-side. From the first page, the editor pulls a dominant-color palette (click-to-sample any pixel as an override), a heuristically detected logo region (drag-to-crop or accept the detection), and — PDF only, not scans — the document's fonts and structural content: sender/recipient labels, an email address, a detected headline, and heading-led sections that become the design's static content.

Branding capture Shipped

Sender name, tagline, accent color, logo, hero image, headline/body font (curated Google Fonts list).

Content extraction Shipped

Style-sample text, static sections, detected headline, sender/recipient/email regex matches. Text-bearing PDFs only — scanned images get colors and a logo, nothing else.

Non-destructive re-import Shipped

Re-uploading a file only fills blanks — it never overwrites a field you've already edited.

Embedded image extraction Built, unused

A real CTM-tracking walk of the PDF locates and crops embedded photos/logos with correct positioning — computed on every import, then dropped before it reaches the design record.

Cosmetic-only control

The setup form's "Save" button is decorative — every field already autosaves on change. It flashes a checkmark but calls nothing.

04Preview & live editing

The editor renders one of two ways, chosen automatically by whether a design has an uploaded source page.

Live-PDF mode (has an uploaded source)

The rendered page image is the preview. Each detected line of text sits under an invisible, precisely-positioned editable overlay — masked to match the surrounding page color until you click in, at which point it reveals itself for editing. Nothing about the original layout, imagery, or color moves.

Templated mode (no uploaded source)

A generic, semantically-styled document assembled from the design's brand tokens and the AI-generated copy fields directly — headline, opening, body paragraphs, closing, static sections.

Gap between the two modes

In live-PDF mode — the common path, since onboarding nudges toward uploading a real document — AI-generated copy has nowhere to go except the headline, which gets auto-written into its matching text block. The opening, bodyParagraphs, and closing the model generates are saved and visible in history, but never appear on the actual document unless someone manually copies them into a block.

05AI generation

Two equivalent entry points — a full form (company + optional notes) and a single-line chat bar — drive the same generation call. Four providers are wired (Anthropic, OpenAI, Gemini, Groq); only ones with a configured API key are offered. The prompt explicitly avoids repeating static sections and treats the design's detected headline as a structural hint, not a template to copy.

History is really "latest per company"

Proposals are stored one row per (design, company) pair. Regenerating for a company you've already generated for overwrites that row — there's no version history, in the editor, in batch generation, or in campaign sends.

06Recipients

A standalone address book, independent of any one design: search, tag-filter, add/edit/delete, and a CSV importer with flexible column-name matching (email, company, first/last name) that dedupes against existing rows by email.

CSV import drops extra columns

Any CSV column beyond the recognized fields is silently discarded rather than folded into custom fields.

07Campaigns & email

A campaign pairs one design with a subject-line template (merge fields like {{company_name}}) and a recipient list, then sends — via Resend or SMTP — generating a proposal on the fly for any recipient who doesn't already have one for that design. Sends embed open-tracking and click-tracking links.

BehaviorStatusDetail
Serial send, no concurrency limitLowNo rate limiting or retry/backoff on individual send failures.
Click-tracking coverageMediumOnly links inside the opening paragraph are tracked — body/closing links aren't, despite the email template supporting it.

08Dashboard

Six rollups — proposals, recipients, campaigns, emails sent, open rate, click rate — above a "continue designing" gallery of recent proposals, styled in each one's own design accent, that jumps straight back into the editor.

Refresh timing

The proposal gallery only refetches when you re-enter the Proposals section from the nav rail, not when you switch to the Dashboard sub-tab from elsewhere inside it — a fresh generation can look stale until you leave and come back.

09PDF export

Two entirely separate export pipelines exist, chosen implicitly by whether the design has an uploaded source page — not by explicit user choice.

The server path needs a locally installed Chrome/Chromium binary — no bundled browser — so it will fail outright on most hosting platforms unless one is separately provisioned.

12Open decisions

  1. Unify PDF export onto one engine, or make the choice between them explicit and font-accurate on both sides.
  2. Give generated body copy a destination in live-PDF mode — map it onto matching blocks by role, or add an explicit insertion affordance.
  3. Decide on real proposal history if multiple versions per company ever need to coexist — the schema would need to change from its current unique-per-company shape.
  4. Collapse the page-state schema duplication once nothing still depends on the legacy single-page columns.

13Non-goals

  • Full rich-text document editing or drag-and-drop layout design.
  • Acting as a CRM — recipients and campaigns exist to drive sends, not to replace one.
  • OCR or content extraction from scanned (non-text) PDFs.
  • True per-event analytics surfacing (individual opens/clicks by IP/user-agent) — the data is logged, but exposing it is out of scope until a use case demands it.

14Recommended next steps

  1. Resolve the PDF export split first — it's the highest-visibility inconsistency (fonts visibly wrong in downloads) and blocks confidently recommending the tool for real sends.
  2. Give body/closing copy a real destination in live-PDF mode, since that's the primary path onboarding drives people toward.
  3. Delete or wire up the dead embedded-image extraction — it's fully built and currently wasted.
  4. Decide the versioned-history question before campaign volume makes the current overwrite-on-regenerate behavior a real support burden.
